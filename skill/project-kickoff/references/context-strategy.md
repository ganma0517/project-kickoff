# Context 管理參考

## 官方功能與本 skill 的規則

Claude Code 的 `/context` 顯示用量。`/compact` 可帶保留重點。接近容量限制時，系統會自動壓縮。實際時機依模型與設定而異。

來源：[Claude Code Context 說明](https://code.claude.com/docs/en/context-window)。查核日期：2026-10-05。

本 skill 的 60% 保存、75% 考慮壓縮是工作預設值。不代表官方設定。使用者可以調整。skill 文字不會修改執行器的壓縮閾值。

## 判斷順序

1. 判斷有沒有新決策、階段成果或驗證結果。確定後立即保存。
2. 判斷目前操作是否到達安全停點。
3. 有可觀察用量時，判斷剩餘空間是否足以完成下一段工作。
4. 沒有用量資訊時，依輸出累積與階段邊界判斷。不要編造用量。
5. 需要空間時，先寫交接資料，再建議壓縮或開新對話。

探索階段可在子任務完成後整理輸出。部署、寫入或其他不能中斷的操作進行中，先減少無關輸出。保存任務識別資訊與狀態。不要重複啟動或盲目重試。

階段完成不代表一定要壓縮。後續工作仍依賴近期上下文且有足夠空間時，可以繼續。

## 交接資料

使用 `assets/PROGRESS.md.template` 的「對話交接」欄位。保存可核對的狀態與證據，不保存內部思考過程。

必要內容：目標、範圍、禁止事項、決策依據、檔案路徑、工具結果識別資訊、進行中操作、未解錯誤、驗證結果與下一步。機密憑證不得寫入交接檔。

逐字對照的內容留在持久檔案。例如審稿原文、變數定義、模型設定或使用者指定的文字。交接檔記錄來源位置。不要把摘要當原文。

## 恢復檢查

接續前讀規則檔與進度檔。按需讀來源檔。檢查路徑仍存在、結果仍有效、背景操作是否結束。尚未確認的事繼續標待確認。

只有核對過的工作可以標為完成。發現狀態不同時先更新進度，再決定下一步。

## 進階框架：膨脹的原因、三層分流、省 token 做法

本節是通用 Agent 工程概念，不是 Claude Code 官方規範。用途是解釋「為什麼」要做前面幾節的事，不是新增規則。教學時可以引用，不要宣稱是 Claude Code 公開承諾的機制。

### 為什麼內容會愈滾愈大

對話型 API 本身無狀態。每次呼叫都要重新打包四層內容：系統與專案規則、工具參數清單、歷史對話、讀入的檔案與錯誤紀錄。對話愈長，新指令只占整包請求的一小部分，其餘都是累積的舊內容——不只耗用量，還會稀釋模型判斷新指令的注意力。

### 三層分流，對應本檔「交接資料」的保留清單

把對話內容分三層，處理方式不同：

- **聊天敘述**：可以自由摘要，細節流失可接受。
- **執行狀態**：用固定欄位記錄，不用自由散文。本 skill 用 `PROGRESS.md` 的固定欄位做這件事。
- **關鍵白名單**：嚴格逐字保留——任務目標與禁止事項、外部 ID／檔案路徑／主鍵、未解決的確切錯誤訊息、失敗路徑與時間戳。這組清單就是「交接資料」一節要求的內容，說法不同，指的是同一件事。

### 三個日常省 token 的做法

1. **丟掉用不到的**：任務換了就開新對話；指令下錯用編輯或回溯清掉錯誤產出，不留在歷史裡；不掛用不到的工具或 MCP server。
2. **縮減留下來的**：先精準檢索，再把結果給模型看，不要整包檔案或整份文件直接灌進去；定案後整理成結構化文字搬進新對話，捨棄中間試錯過程；明確限制輸出範圍。
3. **用好 prompt caching**：同一段系統提示或工具定義重複使用時，快取讀取的成本比重新處理低很多。快取通常有時效，同一任務中途換模型、調整思考強度或改動提示開頭會讓快取失效，這類中途切換能避免就避免。

### 觸發時機怎麼設計：四個層次，愈後面愈不容易丟狀態

壓縮或摘要什麼時候觸發，業界觀察到四個由淺入深的做法。層次愈後面，設計愈複雜，但愈不容易在壓縮當下弄丟重要狀態。這是通用 Agent 工程概念，不是 Claude Code 公開承諾的機制，請自行測試確認實際行為。

1. **依對話輪數**：每隔固定輪數觸發一次。做法最簡單，但跟內容無關——有時候壓得太早，有時候壓得太晚。
2. **依 token 佔比**：設一個比例水位，例如用到上下文上限的 70%～80% 時觸發。本 skill 用 60%／75% 兩個預設值，就是這個層次的做法。
3. **依任務階段切換**：一個子任務做完、要進下一個決策階段時，只打包保留該階段的交付結果，其餘摘要或捨棄。這個做法最自然，也最不容易丟狀態，因為切點剛好是「這段工作已經有結論」的時候。本 skill 的 `PROGRESS.md` 固定欄位，本質上就是在做這件事：階段做完先寫結論，壓縮或換對話才不會傷到還沒定案的內容。
4. **跟任務緊迫程度連動**：觸發頻率不該是固定值，要跟當下工作的緊迫程度一起看。高即時性、高安全要求的操作進行中（例如資料寫入、部署），要避免頻繁壓縮打斷狀態；比較長程的探索或檢索過程，可以適度收斂、提早摘要。本檔「判斷順序」一節的「操作進行中先減少無關輸出、不要重複啟動或盲目重試」，就是這個層次的具體做法。

**為什麼這四層很重要**：壓縮本身一定會遺失一些東西，問題只在遺失的是不是當下工作真正需要的東西。只看輪數或只看 token 比例，壓縮點是跟內容脫鉤的隨機時間點，容易切在工作做到一半、結論還沒定案的地方，壓完才發現關鍵資訊沒了，要回頭重找。依階段切換，壓縮點永遠對齊「有結論可以保留」的時間點，遺失的只會是已經沒用的中間過程。跟緊迫程度連動，則是替高風險操作加一層保護，不讓壓縮在最不該發生的時候發生。四層疊起來用，才能同時兼顧「省空間」跟「不丟真正需要的東西」這兩個互相拉扯的目標。

可以參考的驗證做法：把壓縮後的上下文單獨丟給一次推理，檢查它「選得出正確的下一步、沒踩到禁止事項、能精確復現關鍵證據」。這跟本檔「恢復檢查」一節的精神一致，可以當作更嚴格的驗收方式。
