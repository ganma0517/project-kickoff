# 建檔參考

建立專案檔案時讀取本檔。依使用者答案選用規則。

### 資料夾骨架

依專案類型給預設骨架，沿用使用者既有命名與工具慣例；新專案可建議小寫底線命名、集中存放成品。資料處理依授權與用途決定：

- 受限、含個資或限制尚未釐清的原始資料：保留在獲准位置，處理流程不得覆寫原始檔，不複製到會公開的目錄、不進版控。記錄存取路徑及使用限制；勿把私人絕對路徑寫入公開檔案。
- 公開且獲准使用的資料：可依重現與發布需要保留在原處、複製進專案，或用下載腳本取得。記錄來源、版本／取得日期與授權；複製時保留來源原檔。
- `data_raw/` 可放原始資料路徑說明；只有經確認允許納入專案的資料才放實體檔案。標示「唯讀」只是流程約定，除非實際設定並驗證權限，不聲稱已鎖定檔案。

### 預設資料夾與檔案類型

| 資料夾 | 用途 | 適合存放 | 限制 |
|--------|------|----------|------|
| `backup/` 備份庫 | 獲准內容的手動快照 | .zip、.tar、日期命名副本 | 不自動備份，不複製受限來源；預設不進版控 |
| `data/` 資料庫 | 資料位置說明與獲准資料 | .csv、.json、.dta、.sav、.sqlite | 資料夾不是資料庫服務；受限或未知資料只留存取說明 |
| `figures/` 圖形庫 | 圖表與視覺素材 | .svg、.png、.jpg、.pdf | 記錄來源；保留必要可編輯版本 |
| `src/` 程式庫 | 程式與產生器 | .py、.js、.do、.R | 機密讀環境設定，不寫入程式 |
| `ref/` 參考庫 | 文獻與參考文件 | .pdf、.md、.bib | 遵守來源使用限制 |
| `draft/` 草稿庫 | 尚未完成的文字 | .md、.docx、.tex | 未驗收，不當作成品 |
| `materials/` 教材庫 | 課程與講義 | .md、.pptx、.pdf、.docx | 含個資時按限制處理 |
| `out/` 成品庫 | 交付結果 | .pdf、.html、.svg、.xlsx | 發布前驗收與核對公開內容 |
| `_scratch/` 暫存庫 | 長輸出與探索中間檔 | .log、.txt、.json | 關鍵證據移至持久位置，再清理 |

預設：研究選 data、figures、src、ref、draft、out；開發選 data、figures、src、out；教材選 ref、figures、materials、out。需要快照才選 backup。需要長輸出時選 _scratch。每個選定資料夾建立用途 README；既有資料夾沿用其說明，必要時局部更新。

建立資料夾不代表已執行備份、建立資料庫服務或匯入來源資料。


建資料夾前先檢查環境有沒有對特定路徑的寫入限制（例如 `~/.claude/settings.json` 的 deny 規則）。有些環境會把 `data/` 整個鎖成唯讀來保護受限資料，中間產物放進去腳本會寫不進去，這類限制應該在開工時就發現，而不是跑到一半才踩到。

### 版本管理

會反覆修改、合作或公開的專案建議用 git，尊重使用者選擇；既有 repo 沿用團隊流程，不重新初始化。新 repo 的步驟：

1. 依資料限制與用途寫 `.gitignore`（範本在 `assets/gitignore.template`），在第一次 `git add` 與 commit 前完成排除設定。`git init` 本身不會追蹤檔案。
2. 確認不能進版控的內容：受限原始資料、API key、私用 `.env`、含個資的逐字稿。公開範例、測試資料與資料來源說明按用途決定，不一律排除所有 CSV。
3. 第一個 commit 只納入已確認的骨架、規則與必要檔案；提交前檢查 `git diff --cached` 與 `git ls-files`，提交後回報實際狀態。
4. 大範圍改動前依團隊慣例保存 checkpoint 或開分支；不要為了 checkpoint 提交尚未檢查的敏感內容。

專案如果會轉公開，檢查目前追蹤內容、發布目錄與既有歷史。`.gitignore` 不會移除已追蹤檔案，`git ls-files` 也不能證明歷史沒有機密；若發現疑似外洩，先停止公開，說明發現並提出具體處理方案。

### 本次範圍與里程碑

把訪談結論寫成可執行的計畫，放進 `PROGRESS.md`，不要只列「設計→實作→驗證」：

- **本次範圍**：必須交付的內容，以及明確暫不處理的項目。以使用者需求為準，不自行增加功能。
- **驗收條件**：每項主要產出的可觀察結果、檢查方法及確認者。例：「手機與桌機都能看見案場點位，篩選結果與資料筆數一致，由使用者確認」。發布或交件只是終點，不能取代品質條件。
- **限制與依賴**：截止日期、可投入時間、必要工具／預算／存取權及尚未取得的輸入。未知資訊標待確認，不編造日期、預算或人員。
- **里程碑**：每階段記錄產出、完成條件、前置依賴及下一個具體動作；有期限或多人合作時再補目標日期與負責人。讓第一個里程碑能先驗證關鍵假設。
- **風險與阻礙**：只記與此案相關、可能影響交付的事項，附確認或應對動作。依賴未取得時，明確標示受阻的工作及仍可先做的工作。

小型專案可各用一句話；大型專案再展開表格，不要求每個使用者填完整管理表。期限不足時提出縮小範圍或分期交付選項，待使用者決定，不默默刪掉必要需求。新增需求時先說明對驗收、里程碑與期限的影響，確認範圍變更後更新計畫。

### Context 管理策略

依 SKILL.md 的「協助管理 Context」設定保存、壓縮與接續規則。詳細參考見 [Context 管理參考](context-strategy.md)。在摘要與規則檔記錄此案的逐字保留清單、階段停點與不能中斷的操作。

### 建檔後一致性例子

若來源不得傳給雲端模型，下一步不得直接要求雲端助手讀取；應記錄獲准執行者與本機處理等替代方式。根 README 與各庫 README 若把編碼表分別記為一份與三份，先統一已確認定義。待確認項目記錄最晚確認階段與延後影響。
